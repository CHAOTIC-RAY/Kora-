Architecture

Backend

Three pieces do the network and storage work: a Cloudflare Worker that owns every outbound request, Firebase for accounts and user data, and a plugin system that decides what content exists. This page covers what each piece actually does, and where the boundaries are.

Worker request routing

One Worker serves both the API and the built client. In wrangler.toml, static assets come from ./dist with not_found_handling = "single-page-application", so unknown paths fall back to index.html and client routes such as /share resolve.

The Worker itself is only reached first for two prefixes, set by run_worker_first = ["/api/*", "/send"]:

  1. /api/* — the whole API surface.
  2. /send — the e-reader pairing page. It is in the list because the device browsers it targets are old enough that booting the React bundle to render a short code is slow and a reliable way to hit a syntax error.

Everything else is served as a static asset or falls through to the SPA. Inside the Worker, fetch() reads the URL once, handles OPTIONS as a CORS preflight returning the caller's origin plus Access-Control-Allow-Headers: Content-Type, Authorization, X-API-Key, X-Requested-With, then matches path against a sequence of literal string comparisons.

Route matching is literal, not pattern-based

Endpoints are compared as exact strings such as path === "/api/proxy-image", with a few explicit startsWith checks for families like /api/relay/. There is no router library, so a new endpoint is one if block and the order of blocks is the order of precedence.

Image and file endpoints

Three endpoints exist because a browser on a consumer network cannot reliably reach an archive host directly.

/api/proxy-image

Takes a url query parameter and streams the bytes back as an image. It rejects data: and blob: targets, then applies the shared SSRF guard, then fetches with a browser User-Agent, an image Accept header and a Referer derived from the target origin. The response is cached with Cache-Control: public, max-age=86400.

Any https host is allowed. An earlier per-host allow-list caused every book cover to return 403 in the Android build because the mainstream cover CDNs were not on it, while news thumbnails — served by a separate allow-any endpoint — kept working. The range checks moved into the shared guard instead.

/api/proxy-file

Fetches book files, and is the download path for both the detail sheet and the mirrors list. It accepts GET, HEAD and POST, taking the target from either the url parameter or a download_url JSON body, then normalising it with normalizeMediaUrl.

Audio is a distinct path. When the request asks for audio — an audio=1 parameter, an audio/* Accept header, or an audio-looking URL — it streams with Range support and races several Referer values, because audiobook hosts reject requests that do not look like they came from their own page.

/api/source-fetch

The HTML and JSON relay used by source plugins. It takes u for the target and an optional r for a Referer, requires an http: or https: scheme, applies a 20-second abort, and returns the upstream status, body and final URL as JSON rather than as a proxied response. Returning the body as data lets the client parse it, which a raw byte stream would not.

This endpoint does not use the shared SSRF guard

Unlike /api/proxy-image, /api/source-fetch carries its own four-host blocklist (169.254.169.254, metadata.google.internal, localhost, 127.0.0.1) inline. That is weaker than assertSafeFetchTarget, which range-checks private IPv4 and IPv6 ranges. Treat this as a known gap, not as equivalent protection.

Why relay images at all

Two separate failures, and both are still current. Manga and book CDNs enforce hotlink protection, and createImageBitmap is stricter than an <img> element, so a direct load fails where the element might have limped through. Separately, a DNS filter on some consumer networks answers manhuaplus.com and cdn.manhuaplus.com with a Fortinet "Fortiguard SDNS Blocked Page" certificate, so the browser refuses the handshake with net::ERR_CERT_AUTHORITY_INVALID. Nothing is wrong with the site and nothing is wrong with the selectors — the interception sits between the browser and the origin, and Cloudflare's DNS is not behind that filter.

SSRF guard

Any unauthenticated endpoint that fetches a caller-supplied URL can be aimed at the internal network, where it can read a cloud metadata service for credentials. src/lib/ssrfGuard.ts is the shared guard, and it is layered:

  1. Scheme must be http or https — no file:, gopher: or data:.
  2. Literal IP hosts are range-checked for both IPv4 and IPv6, covering loopback, RFC1918, link-local and CGNAT ranges.
  3. Obvious internal names are refused.
  4. Redirects are not re-validated by hostname, because fetch follows them internally. Callers that must be strict use redirect: "manual" and validate each hop — the mirror probe does exactly this.

It replaced an earlier denylist of four hostnames. That list read as protection while passing 10.0.0.1, 192.168.1.1, 172.16.0.1, [::1], 0.0.0.0 and the whole 127.0.0.0/8 block. assertSafeFetchTarget is shared by /api/proxy-image and the mirror-probe endpoint specifically so the newer endpoint cannot be more permissive than the proxy beside it.

R2 relay and KV

R2 — the e-reader relay

/api/relay and /api/relay/* store files briefly so two devices can meet without either of them holding the whole file. R2 is required rather than optional: the relay stores EPUBs up to 50 MB, and KV cannot, because its value cap is 25 MB and its eventual consistency makes an upload-then-pull flow race with itself.

If the RELAY_BUCKET binding is absent the Worker logs a warning and falls back to per-isolate memory, and /api/relay/status reports {"storage":"memory"} — uploads then do not survive a request boundary.

KV — mirror health

The MIRROR_HEALTH namespace is declared in wrangler.toml for production and shared with the default environment. The intended design is a KvMirrorStore backing recent mirror successes and failures so dead mirrors are tried last.

KV is not wired up yet

resolveMirrorStore in src/lib/mirrorHealthStore.ts still returns in-memory per-isolate storage; the line that would return a KvMirrorStore is a TODO(KV). The binding exists and its id is populated, so enabling it is a matter of implementing that store, not of provisioning anything.

Firebase

Firebase supplies accounts and user data. Authentication is signInAnonymously plus the account surfaces behind Sign in; per-user data lives under users/<uid>/… and is readable and writable only by that uid.

The deployed rules do not match the committed rules

firestore.rules is the intended shape. firestore.rules.proposed is the shape that matches what is actually deployed, and the two differ in a way that has a visible symptom.

Firestore separates get from list:

Observed Firestore operations against the deployed rules
OperationResult
GET users/<own uid>/library/<id>200 — a single document read works
LIST users/<own uid>/library403 PERMISSION_DENIED
LIST communityBooks403 PERMISSION_DENIED
GET communityBooks/<id>200
PATCH users/<own uid>/library/<id>200 — writes work
LIST publicBooks403, though firestore.rules says allow read: if true

The library is read with a query rather than a document read, so every library load is rejected while writes still succeed. That is why a saved book appears to save and then is not there. The fix is allow list, which firestore.rules.proposed spells out for every path in use.

Applying the rules is manual

There is no deploy pipeline for rules in the repository, so firestore.rules.proposed has to be pasted into Firebase console under Firestore → Rules → Edit. Running npm run test:rules checks a rules file against the project's expected allow and deny behaviour, but it does not publish anything.

The room collections — blipRooms, p2pRooms, battleRooms, scrabbleRooms — are deliberately world-writable within a tight shape, because they hold only SDP and ICE signalling for anonymous WebRTC sessions and the room id is the capability. They are unrelated to the library problem.

Plugin system

A plugin adds a source, integration, tool or theme without changing the app. The registry index defaults to https://raw.githubusercontent.com/CHAOTIC-RAY/Kora-Plugins/main/index.json, and additional repositories can be added as plain URLs.

Two runtimes

The two plugin runtimes
RuntimeWhat it does
JSON definition Declarative rules mapping a source's endpoints to results, with URL templates and paging parameters. The injected fetcher makes it testable offline.
Madara A client for WordPress sites running the Madara theme, detected by the theme: "madara" field. Provides popular, latest, search, details, chapters and pages.

Install flow and trust gating

  1. The registry index is fetched and its extensions listed.
  2. Extension metadata is parsed with a positional versionCode split: "106004" with extensionLib: "1.6" is libVersion 1.6 and extension code 4. Parsing it as an integer loses that split.
  3. Installing records the manifest and its sources in local storage.
  4. Readability is judged before an entry is offered, so a source with nothing fetchable behind it is surfaced as such instead of being presented as working.

There is no signature enforcement

RegistryIndex carries an optional signingKey, the SHA-256 of a signing certificate, but it is not verified against a certificate. A user-added repository is treated as self-trusted by explicit product decision, and adding one is a plain URL submission with no confirmation dialog and no first-party allow-list. The sandbox is the point: a source plugin is limited to what a plain fetch could do, so a source cannot exceed the reach of the network it already has.

Catalog search and metadata

Discovery is composed from separate responsibilities rather than one universal catalog. The Worker exposes catalog and search endpoints; Google Books supplies structured metadata when available, with Open Library used as a metadata fallback in supported paths. Other source adapters can contribute downloadable editions, audio items, or reading material according to their own contracts.

ComponentResponsibilityImportant boundary

Request and result flow

  1. The user enters a query. Discover can show temporary session history and title recommendations sourced from Google Books without silently overwriting the typed text.
  2. The client requests metadata or source results through the same-origin API, using bounded retries and caches where implemented.
  3. Results are normalized into the view model and deduplicated using available identifiers and title/author identity.
  4. Opening a result uses the shared detail panel. Metadata enrichment, edition lookup, and mirror resolution can finish asynchronously and must be scoped to the currently selected book.
  5. Downloads are streamed through the configured proxy path where needed. A candidate must be treated as untrusted until its response type and file content are checked.

Upstream availability is not guaranteed

Search metadata, file hosts, and audio sources are independent services. CORS restrictions, quotas, anti-bot responses, expired links, network interruptions, and source-side changes can all cause a request to fail. A useful failure should identify the failing source, preserve the user's query, and offer retry or another available result rather than presenting an empty or misleading success state.

Mirror validation

Some file hosts return landing pages, interstitials, or expired-link pages instead of the requested file. The download path checks MIME information and file signatures where available, isolates partial bytes between mirrors, and can move to another candidate after a failed validation. These checks are a reliability feature, not a malware scanner or a guarantee of copyright status.

Client image routing

A remote image is fetched through the Worker by default, never straight from the browser. resolveCoverImageSrc in src/lib/coverImage.ts passes data:, blob: and already-local paths straight through and routes everything else through /api/proxy-image. Reader pages use the same decision, so a book's cover and a comic's pages cannot disagree about whether to relay.

Proxy-first rather than direct-first is deliberate. On a blocked host every direct attempt is doomed, so a direct-first fallback spends a failed TLS handshake per image before retrying, and the fallback quietly becomes the normal path with extra latency. The proxy costs a Worker invocation, so it is scoped to remote http(s) URLs only; bundled assets and anything already pointing at the Worker are left alone. Re-proxying a Worker URL would produce a self-referential request the proxy rejects with 403, so that check runs first.
