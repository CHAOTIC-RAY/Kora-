Run it yourself

Deploy your own instance

A Kora deployment is a static bundle plus a Cloudflare Worker in front of it, with a Firebase project providing sign-in and storage. This page covers the whole path, in the order you need to do it.

#What you are deploying

Deployment components
PieceWhat it doesRuns on
Web app The reader UI, bundled by Vite Cloudflare static assets, served by the Worker
Worker Search and book APIs, source proxying, the device-to-device relay Cloudflare Workers
Relay storage Holds transferred files until they are pulled once Cloudflare R2 (required)
Mirror health Reliability scores for download mirrors Cloudflare KV
Accounts and data Sign-in, library, reading progress Firebase Auth + Firestore

#Prerequisites

  • Node.js 22 — the version CI builds with.
  • A Cloudflare account, for the Worker, R2 and KV.
  • A Firebase project, for Auth and Firestore.
  • The Firebase CLI (npm i -g firebase-tools) to deploy the security rules.
  • For APK builds only: JDK 21 and the Android SDK.

Get the code:

git clone https://github.com/CHAOTIC-RAY/Kora-.git
cd Kora-
npm install
cp .env.example .env

#Configuration

Build-time settings live in .env. These are read by Vite when the bundle is built, and are compiled into the client — they are not secrets.

Environment variables
VariableRequiredPurpose
VITE_API_BASE_URL Yes Origin the app sends API requests to. Your Worker's workers.dev URL, or your custom domain. The APK forwards /api/* here.
VITE_APP_CHANNEL Yes production or beta. Controls the beta badge and which feature set is offered.
VITE_SENTRY_DSN No Error reporting. Leave empty to disable it. A Sentry DSN is not a secret — Sentry inlines it into every client bundle by design.

A working .env:

VITE_APP_CHANNEL=production
VITE_API_BASE_URL=https://kora.example.workers.dev
VITE_SENTRY_DSN=

Note

If VITE_SENTRY_DSN is unset, error reporting is silently off — nothing warns you. This has been the cause of a build appearing healthy while reporting nothing.

#R2 and KV

R2 — required

The device-to-device relay stores files in R2. Without it the Worker falls back to per-isolate memory, which does not survive a request, so uploads appear to succeed and then vanish. 

npx wrangler r2 bucket create kora-relay
npx wrangler r2 bucket create kora-relay-beta

The binding is already declared in wrangler.toml as RELAY_BUCKET. Keep the bucket names matching, or update the bucket_name values to your own.

KV is used for mirror reliability scores. It is optional — mirrors report as unverified without it rather than failing.

KV — optional

npx wrangler kv namespace create MIRROR_HEALTH

Paste the returned namespace id into wrangler.toml as the id for the MIRROR_HEALTH binding, replacing the value committed there.

#API keys

The book-search key is optional. Kora searches without one — see the fallback chain for what you get. Setting it is a Cloudflare secret, not an environment variable: the Worker reads it and it is never compiled into the bundle. 

npx wrangler secret put RAVE_API_KEY

Wrangler prompts for the value and stores it encrypted. It is sent in an X-API-Key header and must stay server-side: anything prefixed VITE_ ends up in the public bundle.

For local development, put secrets in .dev.vars (gitignored):

RAVE_API_KEY=your-key-here

#What works without a key

Kora runs with no Rave key at all. Search, discovery and downloads all work; the only thing you lose is access to the key-authenticated v1 endpoint. The chain, in the order a search tries it:

  1. Rave v1 — /api/v1/search, requires the key. Tried first, on the canonical host and then on the legacy Worker host. The two are raced against each other, so a host that is not answering does not delay the search.
  2. Rave legacy — /search/all. Needs no key, aggregates the same set of mirrors. This is what serves search on a keyless install.
  3. LibGen — resolved through signed CDN links, which expire and are re-minted per request by racing mirrors.
  4. Internet Archive — direct items, surfaced as their own mirror.
  5. Anna's Archive, LibreTexts and Open Library — reached through the source endpoints and the Worker proxy.
  6. Project Gutenberg — reachable as a source=all mirror, so public-domain titles appear alongside everything else.

The response tells you which one answered

Every search response carries an engine field — "v1", "legacy" or "none" — plus fallback, which is true whenever the engine is not v1. The UI labels results from that field rather than assuming v1, so a keyless install shows neutral wording ("Open Catalog Mirror") instead of claiming a Rave result it never fetched. Check it yourself: 

curl "https://your-worker.workers.dev/api/annas-archive/search?q=dune&source=all&page=1"

The v1 endpoint is unreliable, not dependable

v1 is genuinely slower and fails outright on roughly half of queries; the legacy endpoint's own response time has been measured anywhere from 7 to 24 seconds. That is why the three rungs race against a single shared 28-second budget instead of running in sequence — a sequential ladder can spend every timeout and still return nothing. In a ten-query sample against the deployed Worker, v1 answered six and the legacy endpoint answered the rest.

Plan for the legacy path being the one that usually serves you. Do not describe a keyless or v1-backed install as "search always hits v1" — that has not been true in measurement.

#Deploy the Worker

Build and deploy production:

npm run deploy:prod

Or step by step, which is what the script does:

npm run build:data     # splits the dictionary bundle
npx vite build         # builds the client into dist/
npx wrangler deploy --env production

For a beta Worker on its own domain:

npm run deploy:beta

Run it locally against the real Worker runtime:

npm run cf-dev

wrangler.toml serves the SPA from dist/ and routes /api/* and /send through the Worker first. /send goes Worker-first because it has to work on old device browsers, and loading the whole bundle to display a 4-character code is slow and fragile on those.

#Firestore rules

Security rules are not deployed by the build. Deploy them explicitly, or the app will run against whatever rules were last published: 

firebase deploy --only firestore:rules

Log in first with firebase login, and make sure firebase use points at your project.

Known gap: library queries are denied

The rules currently deployed to the upstream project grant get but not list. Reading one document by id succeeds; querying a collection is denied. Loading the library therefore fails with a permission error.

A corrected rules file is committed as firestore.rules.proposed. To apply it: 

cp firestore.rules.proposed firestore.rules
firebase deploy --only firestore:rules

Check the rules behave before deploying them: 

node scripts/test-firestore-rules.mjs

#Build the APK

The Android build is assembled by GitHub Actions, not by hand. Pushing to main or beta with a change under android/, src/, public/, index.html, vite.config.ts, capacitor.config.ts or the package files triggers it.

To enable it on your fork:

  1. Create a repository secret KORA_UPLOAD_KEYSTORE_BASE64 containing your upload keystore, base64-encoded.
  2. Add KORA_KEYSTORE_PASSWORD, KORA_KEY_ALIAS and KORA_KEY_PASSWORD as secrets too.
  3. Optionally set a repository variable VITE_API_BASE_URL so the APK points at your Worker. It falls back to the upstream URL if unset.
  4. Push to main, or run the Build Android APK workflow manually.

The keystore committed at android/app/keystore/kora-ci.jks is intentionally invalid, and the Gradle config refuses to fall back to it. A release build fails rather than signing with a throwaway key.

Building an APK locally, if you need to:

npm run apk:release

Version numbers come from the build, not from a file you edit: 1.0.<build number>, and the Android version code is the build number itself.

#Troubleshooting

Common deployment problems
SymptomCause and fix
Relay upload succeeds, file never arrives The RELAY_BUCKET binding is missing, so the Worker is using in-memory storage. Check the Worker log for RELAY_BUCKET binding is absent, and GET /api/relay/status — it reports {"storage":"memory"} instead of r2. Create the bucket and redeploy.
Library empty, console shows a permission error The deployed rules lack list. Deploy firestore.rules.proposed as shown in Firestore rules.
All mirrors show UNVERIFIED The MIRROR_HEALTH KV namespace id is wrong or the binding is absent. This is not fatal — mirrors stay clickable, they just have no reliability data.
No errors reported in Sentry VITE_SENTRY_DSN was empty at build time. It has to be set in the environment the build ran in, and the client rebuilt.
APK talks to the upstream server VITE_API_BASE_URL was not set for the build. Set the repository variable and rebuild.
Book search slow or rate-limited Check the engine field in the response. On the legacy endpoint a slow response is upstream behaviour, not a misconfiguration — measured between 7s and 24s. A key widens the chance of the faster v1 rung answering, but does not remove the legacy path.
Book search returns nothing at all engine is "none", meaning every rung failed. Both Rave endpoints are bursty upstream, so retry. If the key is present, confirm it is a Worker secret and not a VITE_ variable — anything prefixed VITE_ is compiled into the public bundle.
